# DynamoDB access patterns (SCFRMS-28 draft)

## Scope and key terms

This proposal maps the current [OpenAPI contract](../api-specs/openapi.yaml) to DynamoDB operations. It is not a deployed schema. A **partition key (PK)** groups items queried together. A **sort key (SK)** orders items within that group. A **global secondary index (GSI)** offers another PK/SK for a different query, with eventually consistent reads. `Query` needs a PK value; `GetItem` reads one known key. A filter expression does not make an unbounded scan efficient.

Use opaque, stable IDs for tickets, photos, events, accounts, and teams. Composite sort-key _values_ use UTC ISO 8601 timestamps followed by an ID to break ties; the attribute names are specified below. Never use location text as a key: it is reporter-entered free text, and spelling variants are distinct. Do not introduce `zoneId` without a new requirement.

## Proposed tables and indexes

| Table             | Base key                                                | Additional access path                                                                                                                                                                 | Purpose                                                                                                                                                                                                                                                                    |
| ----------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Tickets`         | PK `ticketId`                                           | `TeamOpenIndex`: PK `teamStatusKey` = `TEAM#<teamId>#STATUS#<status>`, SK `createdKey` = `<createdAt>#<ticketId>`; `CreatedMonthIndex`: PK `createdMonth` = `YYYY-MM`, SK `createdKey` | Current ticket snapshot, free-text `location`, routing, priority, `triagedAt`, optional deadline, merge target, version, and repair-cycle counters. Only ASSIGNED and IN_PROGRESS tickets have `teamStatusKey`. Every ticket has `createdMonth`, including merged sources. |
| `TicketReporters` | PK `ticketId`, SK `reporterLineUserId`                  | `ReporterTicketsIndex`: PK `reporterLineUserId`, SK `associatedKey` = `<associatedAt>#<ticketId>`                                                                                      | Ticket visibility and LINE notification recipients. Preserve original associations and copy source reporters to the canonical ticket on merge; store `sourceTicketId` as provenance.                                                                                       |
| `TicketPhotos`    | PK `ticketId`, SK `photoId`                             | None initially                                                                                                                                                                         | S3 object key, purpose (DEFECT or REPAIR_PROOF), upload time, and repair cycle. Source photos stay on source tickets after a merge.                                                                                                                                        |
| `TicketEvents`    | PK `ticketId`, SK `eventKey` = `<occurredAt>#<eventId>` | None initially                                                                                                                                                                         | Append-only status, triage, assignment, priority, completion, reopen, and merge events, with actor account/team, before/after values, reason, proof-photo ID, and repair cycle.                                                                                            |
| `Accounts`        | PK normalized `username`                                | None initially                                                                                                                                                                         | One account per team under the current plan; stable `accountId`, `teamId`, role, password hash, active flag, token version, and lockout fields. Manager account membership needs a rule.                                                                                   |
| `Teams`           | PK `teamId`                                             | None initially                                                                                                                                                                         | Team name and active flag; assignment validates this record.                                                                                                                                                                                                               |

The team index is **sparse**: RECEIVED tickets have no team, and DONE/MERGED tickets leave the open queue. ASSIGNED and IN_PROGRESS are separate partition values. The month index supports chronological manager history without a full table scan, but an unrestricted range walks month partitions and needs a cursor containing the current month and DynamoDB continuation key. Index projections should carry list-card fields only; fetch a ticket for full details. Do not return raw LINE IDs or S3 keys to clients.

## API access patterns

| Request or workflow              | DynamoDB operation                                                                                                                                 | Important behavior                                                                                                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Create ticket                    | Conditional `PutItem` in `Tickets`; add original `TicketReporters` association, defect-photo metadata, and creation event                          | Use a transaction for bounded writes. Start at RECEIVED, repair cycle 1, version 1, and keep the reporter's free-text location.                                                |
| `GET /tickets/{ticketId}`        | `GetItem` ticket; for a reporter, strongly consistent `GetItem` of `TicketReporters` at (ticket ID, verified LINE user ID); query photos           | A ticket ID alone never grants access. A merged source stays readable through its own association.                                                                             |
| Reporter `GET /tickets`          | `Query ReporterTicketsIndex` by verified LINE user ID; batch-get ticket snapshots                                                                  | The GSI is eventually consistent, so a new or copied association may appear after a short delay. Verify authorization against the base association for detail and photo reads. |
| Team open queue                  | `Query TeamOpenIndex` for ASSIGNED and IN_PROGRESS partitions; combine pages if the UI needs one list                                              | Assignment, reassignment, completion, and reopening update the ticket and index attributes together. RECEIVED belongs in manager intake, not a team queue.                     |
| Staff ticket/photo detail        | `GetItem` ticket, check role/team and merged-source rules, then `GetItem` photo metadata                                                           | Generate a short-lived S3 read URL only after authorization.                                                                                                                   |
| Audit and older repair cycles    | `Query TicketEvents` and `TicketPhotos` by ticket ID                                                                                               | Reopening increments cycle and appends events; never overwrite earlier DONE events or proof photos.                                                                            |
| Merge duplicates                 | Read source tickets and associations; mark sources MERGED, set `mergedIntoTicketId`, copy source reporter associations to canonical, append events | Preserve original reports/photos. Use conditional writes and an idempotency key. A large merge may exceed one transaction; decide a limit or resumable workflow first.         |
| Manager history by creation date | `Query CreatedMonthIndex` across month buckets; fetch snapshots and event-derived counters                                                         | Includes current, reopened, and merged-source records. Exact counts for arbitrary filters are **not solved** by this index.                                                    |
| Staff login                      | `GetItem Accounts` by normalized username; verify hash and account state                                                                           | `accountId` identifies the shared credential, not the individual technician who used it.                                                                                       |

Use conditional writes on `Tickets.version` for status, assignment, priority, reopen, and merge changes. Pair each state change with its audit event in a transaction where within DynamoDB limits. Request idempotency storage for create/merge and other retried mutations needs a separate decision on key scope, retention, and response replay. Upload intents also need ownership, expiry, and single-use checks before attaching an S3 object; storage for those intents is a separate design decision.

## Decisions needed before creating AWS resources

1. **Dashboard counts and filters.** The current API promises exact all-matching totals and breakdowns for arbitrary combinations of date, status, free-text location, and team. The month index with post-filtering cannot provide these cheaply over large histories. Choose a bounded reporting scope or a dedicated reporting projection/analytics store, then define update and consistency rules. Current dashboard counts could use transactional counter items once dimensions are fixed; do not infer historical totals from one page.
2. **Staff list semantics.** `GET /tickets` allows status, location, team, and completion-date filters. Specify required combinations and sort order before adding more GSIs. `TeamOpenIndex` does not support every combination or completion-date lookup.
3. **Triage representation.** The proposed flow is RECEIVED until classification and routing succeed, then ASSIGNED with `triagedAt` and a triage event. Classification failure leaves the ticket RECEIVED. Confirm whether a separate TRIAGED status is wanted; the current API has none and does not expose `triagedAt`.
4. **Shared account contract.** The API names `acceptedByStaffId` and `actorStaffId`, suggesting individual attribution. Decide whether to rename them to account IDs and accept team-level attribution, or add individual sign-in later. Set the manager account role/team rule too.
5. **SLA and notifications.** Keep `deadlineAt` optional until priority durations and reopen rules are approved. Decide which status changes trigger LINE Messaging API sends, whether every associated reporter is notified after merge, and how retries/failures are recorded. Notification delivery should not block a ticket transition.
6. **Merge and consistency limits.** Confirm cross-team merges, maximum source/association counts, reporter visibility on canonical tickets, and whether delayed GSI list visibility is acceptable. Authorization checks still use strongly consistent base-key reads.

## First implementation slice after decisions

Create the minimal tables and indexes for confirmed reporter and team flows. Implement create/get/list, conditional transitions with audit events, and repository tests for authorization, retries, concurrent updates, reopened history, and merge association preservation. Add manager reporting indexes or projections after the dashboard contract and expected volume are known.
