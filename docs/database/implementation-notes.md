# Backend implementation notes

What the backend code stores and reads today (SCFRMS-40, 41, 43, 45, 46, the SLA-02 safety override and the SR-31 rate limit). The table keys follow the proposal in [DynamoDB access patterns](dynamodb-access-patterns.md) (SCFRMS-28). This file only records what the code does and where it adds to that proposal; additions are marked as proposals for team review. Nothing here has been run against real AWS yet; the tests use mocks.

## Tables used

Each table name comes from an environment variable (`backend/src/shared/tables.ts`), so the infrastructure decides the real names.

| Table             | Environment variable          | Keys and indexes                                                                                                   | Written by                                  |
| ----------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| `Tickets`         | `TICKETS_TABLE_NAME`          | PK `ticketId`; `TeamOpenIndex` (`teamStatusKey`, `createdKey`); `CreatedMonthIndex` (`createdMonth`, `createdKey`) | `POST /tickets`, AI triage, status endpoint |
| `TicketReporters` | `TICKET_REPORTERS_TABLE_NAME` | PK `ticketId`, SK `reporterLineUserId`; `ReporterTicketsIndex` (`reporterLineUserId`, `associatedKey`)             | `POST /tickets`; read by the LINE channel   |
| `TicketPhotos`    | `TICKET_PHOTOS_TABLE_NAME`    | PK `ticketId`, SK `photoId`                                                                                        | `POST /tickets`, status endpoint (`DONE`)   |
| `TicketEvents`    | `TICKET_EVENTS_TABLE_NAME`    | PK `ticketId`, SK `eventKey` = `<occurredAt>#<eventId>`                                                            | `POST /tickets`, AI triage, status endpoint |
| `Notifications`   | `NOTIFICATIONS_TABLE_NAME`    | PK `ticketId`, SK `notificationKey` = `<eventId>#<channel>:<recipient>`                                            | notification worker (proposal)              |
| `RateLimits`      | `RATE_LIMITS_TABLE_NAME`      | PK `limitKey`, SK `windowStart` (number); TTL attribute `expiresAt`; no stream                                     | `POST /tickets` (proposal)                  |
| `Teams`           | `TEAMS_TABLE_NAME`            | PK `teamId`; `email` is a proposed field                                                                           | read by the notification worker (proposal)  |
| `Accounts`        | `ACCOUNTS_TABLE_NAME`         | PK normalized `username`                                                                                           | staff login (`shared/accounts.ts`)          |

## Accounts

One item per staff account, PK `username` (trimmed, lower case). The staff login takes `email` from the request body and uses it as the username.

| Attribute                                                    | Notes                                                                                   |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `accountId`                                                  | Stable id, put in the staff token and in audit events                                   |
| `role`                                                       | `TECHNICIAN` or `MANAGER`                                                               |
| `teamId`                                                     | `TECHNICIAN` only (SR-07: one shared account per team); never a manager                 |
| `displayName`                                                | Shown in `StaffProfile.name`                                                            |
| `passwordHash`                                               | bcrypt, cost 12 (SR-09); the password is generated by the system, 12 characters or more |
| `isActive`, `tokenVersion`                                   | Checked on every staff request (SR-10)                                                  |
| `failedLoginCount`, `lockedUntil`                            | The fifth failed login in a row locks the account for 15 minutes                        |
| `passwordChangedAt`, `lastLoginAt`, `createdAt`, `updatedAt` | UTC ISO 8601                                                                            |

`shared/accounts.ts` reads the account with a strongly consistent read, and counts failures and locks with conditional updates, so parallel wrong guesses cannot get past the limit. An item that does not fit this model makes the read throw (a `500`), so a data error is not mistaken for a wrong login. `shared/password.ts` hashes and checks passwords, and a check against an unknown username does the same work as a real one, so response time does not reveal which accounts exist.

**Seeding the first accounts (SR-07).** Nobody can log in until an account exists, and the manager endpoints that should create accounts (RR-13) are not built, so `backend/src/scripts/seed-accounts.ts` does it:

```
npm run seed:accounts -w @scfrms/backend -- \
  --manager-email manager@example.com --manager-name "Juristic manager" \
  --teams-domain example.com
```

It creates the personal `MANAGER` account and, with `--teams-domain`, one shared `TECHNICIAN` account for each of the 5 teams (`electrical@`, `plumbing@`, `hvac@`, `cleaning-sanitation@`, `building-equipment@` at that domain). It needs `ACCOUNTS_TABLE_NAME` and AWS credentials from the environment or the root `.env` (and `DYNAMODB_ENDPOINT` for DynamoDB Local). Every password is generated by the script (20 characters), printed once and never stored; only the bcrypt hash is. Hand each one over in person (SR-09). An account that already exists is skipped and keeps its password, so running it again is safe and resets nothing. Changing a password later (raise `tokenVersion`) needs the manager endpoints, which do not exist yet. The script was run against a fake DynamoDB endpoint only, not a real table.

## Tickets

**Ticket id.** `tkt_` plus the first 26 hex characters of `sha256(lineUserId + "\n" + Idempotency-Key)`. A retry with the same key reaches the same item; two reporters using the same key never collide.

**Create (`POST /tickets`).** One transaction writes the ticket (conditional on `attribute_not_exists(ticketId)`, so a duplicate id cancels everything), the reporter link, one `TicketPhotos` item per defect photo and a `CREATED` event. The ticket starts as `RECEIVED`, `repairCycle` 1, `version` 1. The same payload replayed gets the original `201`; a different payload with the same key gets `409`.

**Read.** `getTicket` reads the ticket and queries its photos, both strongly consistent, and returns one record with an embedded photo list. Callers never see storage attributes.

**Fields stored on the ticket.** The fields of the `Ticket` schema in `openapi.yaml`, plus:

- storage attributes: `ticketId` (the key), `createdMonth` (`YYYY-MM`), `createdKey` (`<createdAt>#<ticketId>`), and `teamStatusKey` (`TEAM#<teamId>#STATUS#ASSIGNED` from triage, `TEAM#<teamId>#STATUS#IN_PROGRESS` while the work is in progress, removed at `DONE`; it puts the ticket in `TeamOpenIndex`);
- internal fields, never returned to callers: `reporterLineUserId` (the original reporter), `version` (optimistic-locking counter), `safetyHazard` (SLA-02, below), and on each photo `s3ObjectKey`;
- set at triage: `slaPolicyVersion`, `triagedAt`, and `prioritySetBy` (`AI`; a staff change sets `STAFF`). `prioritySetBy` is part of the `Ticket` schema;
- set by the status endpoint: `completedAt` (`DONE`).

**Uploaded images.** An upload lives at S3 key `uploads/<purpose>/<ownerId>/<uploadId>`, where `<purpose>` is `DEFECT` or `REPAIR_PROOF` and `<ownerId>` is the uploader's LINE user ID or staff account ID. An object existing at that key proves its purpose and owner, so `POST /tickets` only checks existence, while the `DONE` status also reads the first bytes of the object and accepts only a JPEG, PNG or WebP (SR-21; `uploadIsImage()`). `POST /uploads` must create objects at exactly this key (`uploadObjectKey()` in `backend/src/shared/upload-store.ts`).

## Staff endpoints (SCFRMS-43)

A technician starts and finishes the work on a ticket of their team. Acceptance is team-level (the team decision of the staff UI, one shared account per team under SR-07), so there is no accept step. The handler is `backend/src/tickets/set-status.ts`. It is not routed yet: `local.ts` only serves `/health`, and the API Gateway routes belong to the infrastructure.

**Staff token (SR-08).** Every staff endpoint reads the caller's role and team from a signed token and never from a request field. The token is a JWT signed with HMAC-SHA256 using `STAFF_JWT_SECRET` (at least 32 characters; SR-34 says it lives in Secrets Manager). The staff login that issues it is `POST /auth/staff/login` (below); it calls `signStaffToken()` in `backend/src/shared/staff-token.ts`.

| Claim           | Meaning                                                             |
| --------------- | ------------------------------------------------------------------- |
| `account_id`    | The shared team account or a manager account                        |
| `role`          | `TECHNICIAN` or `MANAGER`                                           |
| `team_id`       | Required for a `TECHNICIAN`, left out for a `MANAGER`               |
| `token_version` | Raised on a password reset or when an account is disabled (SR-10)   |
| `iat`, `exp`    | Seconds since the epoch; a token lives 12 hours at most (60 s skew) |

A bad, expired or wrongly signed token is `401` with one generic message.

**Account check on every request (SR-10).** A valid signature is not enough. `requireStaff()` in `backend/src/shared/staff-auth.ts` reads the account named by `account_id` and answers the same `401` unless the account exists, is active, and has the same `token_version`, role and team as the token. So disabling an account, resetting its password (raise `tokenVersion`) or changing its role or team stops its old tokens at once, not after 12 hours. The role and team the endpoint uses come from the account. The token's `account_id` is looked up as the `Accounts` key, so an account's `accountId` must be its normalized username (a proposal to the team, see Who needs to do what); the token check costs one strongly consistent read per request. A locked account (failed logins) can still use a token it already holds: the lock only stops new logins.

**`POST /auth/staff/login`** (body `{ "email": "...", "password": "..." }`, handler `backend/src/auth/staff-login.ts`). The email, trimmed and lower-cased, is the key of the `Accounts` table. On success the answer is `200` with `{ accessToken, expiresInSeconds: 43200, staff: { id, name, role, teamId } }` and `Cache-Control: no-store`; `teamId` is left out for a manager. The success also stores `lastLoginAt` and clears the failure count.

| Status | When                                                                                                                                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `400`  | Body is not a JSON object, an unknown field, an email without `@` or over 254 characters, no password or one over 128 characters         |
| `401`  | Wrong email, wrong password, or a disabled account: one message for all three, so an answer never says which accounts exist              |
| `429`  | The account is locked (`RATE_LIMITED`, with `Retry-After` in seconds), also for the right password, and on the fifth failed login itself |

A wrong password counts one failure. A login for an unknown email, or for a disabled account with the right password, counts nothing. A check against an unknown email does the same bcrypt work as a real one. Known limits: the lock exists only for real accounts, so a client that hits `429` after five tries learns that the email exists (the per-IP limit of SR-09, an AWS WAF rule on API Gateway, slows this down but is not code); and there is no manager MFA yet (SR-09).

**`GET /auth/staff/me`** (handler `backend/src/auth/staff-me.ts`). Returns `{ id, name, role, teamId }` (`StaffProfile`) read from the current account, so a changed display name shows at once; `teamId` is left out for a manager. `401` for a missing or bad token, a disabled account or an old `token_version`. The profile has no `teamName`: the staff UI asked for one, which needs a `name` field on the `Teams` table first.

**`PATCH /tickets/{ticketId}/status`** (body `{ "status": "IN_PROGRESS" | "DONE", "proofPhotoUploadId": "..." }`). Any `TECHNICIAN` of the ticket's team may do it; a manager or a technician of another team gets `403`. The allowed moves are `ASSIGNED` to `IN_PROGRESS` and `IN_PROGRESS` to `DONE`; anything else is `409`.

- `IN_PROGRESS` puts the ticket in the team's `IN_PROGRESS` queue (`teamStatusKey`).
- `DONE` needs `proofPhotoUploadId`: a `REPAIR_PROOF` upload at `uploads/REPAIR_PROOF/<accountId>/<uploadId>` of the calling account whose first bytes are a real image (SR-21), otherwise `422`. It removes the ticket from the open queue, sets `completedAt` (the SLA clock stops, SLA-11) and stores the photo in `TicketPhotos` with `repairCycle`.
- Asking again for the status the ticket already has (for `DONE`, with the same photo) gets `200` with the ticket as it is, so a retry after a lost response does not fail.
- The ticket update, the `STATUS_CHANGED` event and the proof photo are one transaction, conditional on the expected status and the `version` that was read, so when two requests race exactly one wins. The event records the calling account as `actorStaffId` and, for a technician, the team as `actorTeamId` (SR-11).

| Status | When                                                                                  |
| ------ | ------------------------------------------------------------------------------------- |
| `400`  | Bad body, unknown field, missing proof photo for `DONE`, proof photo on `IN_PROGRESS` |
| `401`  | Missing, bad or expired staff token, or the account is disabled or its token is old   |
| `403`  | Manager, or a technician of another team                                              |
| `404`  | Unknown ticket                                                                        |
| `409`  | Wrong current status for the move, or a lost race                                     |
| `422`  | Proof photo is not a completed `REPAIR_PROOF` image upload of the caller              |

**Audit events.** Every event id carries what keeps it unique: a ticket can go through the same step again after a reopen or a reassignment, and each time it gets a new event.

| Kind             | Written by      | Event id                       | Extra fields                                                            |
| ---------------- | --------------- | ------------------------------ | ----------------------------------------------------------------------- |
| `CREATED`        | `POST /tickets` | `<ticketId>_created`           | `toStatus`                                                              |
| `TRIAGED`        | AI triage       | `<ticketId>_triaged`           | `fromStatus`, `toStatus`, `toPriority`, `toTeamId`                      |
| `STATUS_CHANGED` | status          | `<ticketId>_status_v<version>` | `fromStatus`, `toStatus`, `actorStaffId`, `actorTeamId`, `proofPhotoId` |

`<version>` is the version the ticket has after the change. The notification worker reads `toStatus` and `proofPhotoId` from the stream record.

**Who sees what.** Responses are built by `toTicketView()` in `backend/src/tickets/ticket-view.ts`, an allowlist of the `Ticket` schema fields. Internal fields (`reporterLineUserId`, `version`, `safetyHazard`, photo S3 keys) never reach a caller.

**Decisions and gaps**

- The audit event for a new ticket is named `CREATED`, not `TICKET_CREATED`, because the staff UI's history timeline shows `CREATED` as "Report received via LINE". The other two kinds in use (`TRIAGED`, `STATUS_CHANGED`) already match the staff UI.
- The staff login takes `email`, as `openapi.yaml` and the staff UI do (the requirements document says `username`; the email is used as the `Accounts` key). The priority is named `CRITICAL`, as in `openapi.yaml` and the staff UI (the requirements document says `HIGH`); the AI's impact and urgency levels still use `HIGH`, `MEDIUM` and `LOW` and the matrix maps the top result to `CRITICAL`.
- A manager cannot change a status. The requirements document (RR-12 and its permission matrix) lets a manager do it on any ticket, but `openapi.yaml` says an override needs a separate exception policy, and the team follows `openapi.yaml`. Confirm with the team if managers should be able to override.
- A technician of another team gets `403`, not `404`. The staff UI expects `403` for another team's job (its README, steps 6 and 8), and the team follows the frontend here. The requirements document (SR-13) asks for `404` so that ticket ids cannot be probed; that is not followed on this endpoint.
- `actorTeamId` is an addition to the `TicketEvent` schema of `openapi.yaml`, which has only `actorStaffId`. The access patterns document and SR-11 ask for the actor's team.
- SR-11 also asks the staff portal to ask "who is working?" at login and keep the typed name in the audit event as an unverified label. That is not built: the login body of `openapi.yaml` has no such field.
- Within one ticket a proof photo id can be stored only once (the photo write is conditional), but nothing stops the same upload from being attached to a different ticket. Single-use uploads (SR-21) need a registry that `POST /uploads` does not have yet.
- `POST /tickets` still only checks that the defect upload exists; the image signature check of SR-21 is not applied there yet.
- There is no accept step: the staff UI team proposed removing `POST /tickets/{ticketId}/accept`, `acceptedByStaffId` and `acceptedAt` because every technician of a team shares one account, and the team agreed. `openapi.yaml` still lists them until its owner removes them.
- The reopen endpoint, the photo access endpoint and the staff login are not built (see Who needs to do what).

## Rate limit (SR-31, proposal)

`POST /tickets` lets one reporter create 10 tickets per hour (`TICKET_RATE_LIMIT_PER_HOUR`, default 10); the next one gets `429` with code `RATE_LIMITED` and a `Retry-After` header in seconds. The count is one `RateLimits` item per reporter and clock hour (a fixed window), incremented by a single conditional update, so parallel requests cannot pass the limit. Only a request that would create a ticket counts: a retry of an existing ticket (same `Idempotency-Key`), an invalid request and a failed upload check do not. A reporter can send up to twice the limit around the turn of an hour. The per-IP limit of SR-31 is an AWS WAF rule on API Gateway and is not part of this code. The table needs DynamoDB TTL enabled on `expiresAt` (epoch seconds) and must have no stream, so counting never starts a worker.

## Stream consumers

- **AI triage** is triggered by the `Tickets` stream. Every `INSERT` is a new ticket; `MODIFY` events are ignored, which also stops the triage update from re-triggering itself.
- **Notifications** are triggered by the `TicketEvents` stream. Every `INSERT` is an audit event, and its `kind` decides which channels fire (work order email, LINE messages). The `Notifications` and `RateLimits` tables are separate and have no consumer.

Both event source mappings need `ReportBatchItemFailures`, a stream view of `NEW_IMAGE` or `NEW_AND_OLD_IMAGES`, a bounded retry count and a small batch size (1-5, because each ticket makes sequential AI calls).

## AI triage (SCFRMS-41)

A new ticket is stored as `RECEIVED` with no category, priority or team. A worker then classifies it and moves it to `ASSIGNED`. Bedrock never writes to DynamoDB: it only proposes values, and backend code validates them and writes the result.

**Flow**

1. The `Tickets` stream delivers the `INSERT`.
2. The worker skips the ticket unless it is still `RECEIVED`, so duplicate stream deliveries cost nothing.
3. Rekognition (`DetectLabels`) reads the defect photo from S3 and returns object labels. If this fails, classification continues from the text alone.
4. Bedrock (Converse API) receives the location, description and labels and replies with `{category, impact, urgency}`. The resident's text is passed as quoted data, never as instructions.
5. Backend code accepts only known values, then computes the rest (below) and writes it in one transaction.

**Rules applied in code** (`backend/src/triage/policy.ts`; proposed defaults from the Security, Roles & SLA requirements, to be confirmed by the juristic office)

| Impact \ Urgency | HIGH     | MEDIUM   | LOW    |
| ---------------- | -------- | -------- | ------ |
| HIGH             | CRITICAL | CRITICAL | MEDIUM |
| MEDIUM           | CRITICAL | MEDIUM   | LOW    |
| LOW              | MEDIUM   | LOW      | LOW    |

| Priority | Hours from `createdAt` to `DONE` |
| -------- | -------------------------------- |
| CRITICAL | 4                                |
| MEDIUM   | 24                               |
| LOW      | 120                              |

The deadline is counted from ticket creation, so slow triage uses up SLA time. The requirements document calls the top priority `HIGH`; `openapi.yaml` calls it `CRITICAL`, and the team chose `CRITICAL`. Each category maps to the team of the same name: `ELECTRICAL`, `PLUMBING`, `HVAC`, `CLEANING_SANITATION`, `BUILDING_EQUIPMENT`.

**Safety override (SLA-02).** Before the matrix is applied, `backend/src/triage/safety.ts` scans the description for English keywords of a safety hazard: `FIRE`, `SMOKE`, `GAS`, `ELECTRIC_SHOCK`, `FLOOD_NEAR_ELECTRICAL` (water together with electrical equipment) or `TRAPPED`. If one matches, `priority` is `CRITICAL` whatever the matrix says, and the deadline is the CRITICAL one (4 hours from `createdAt`). `suggestedPriority` still holds the matrix result. The scan runs in code on the resident's text, not in the AI, so a crafted description cannot lower it. Phrases that name safety equipment (for example "fire extinguisher") or an air-conditioning gas refill do not trigger it.

**Fields set on the ticket.** `status = ASSIGNED`, `category`, `suggestedPriority`, `priority`, `prioritySetBy = AI`, `teamId`, `deadlineAt`, `slaPolicyVersion`, `triagedAt`, `updatedAt`, `version + 1` and `teamStatusKey`. When the safety override applied, `safetyHazard` is also set. It is internal: it is never returned to callers.

**Audit event.** A `TRIAGED` event in `TicketEvents` with `actorType = SYSTEM`, `fromStatus = RECEIVED`, `toStatus = ASSIGNED`, `toPriority`, `toTeamId`, and `note = SAFETY_OVERRIDE:<hazard>` when the override applied (`note` is part of the `TicketEvent` schema). The ticket update and the event are one transaction, conditional on `status = RECEIVED` and the `version` that was read, so a concurrent change makes the whole write fail and nothing is applied twice.

**Failures**

| Case                                                     | Result                                                                         |
| -------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Reply is not JSON, or a value is outside the known lists | Ticket stays `RECEIVED`, logged, not retried. Find it with `?status=RECEIVED`. |
| Ticket not found                                         | Logged, not retried.                                                           |
| Same as the first row, but a safety hazard was detected  | Same, and logged as `Safety hazard report needs manual triage`.                |
| Temporary error (Bedrock throttling, DynamoDB)           | Reported as a batch item failure; Lambda retries from that record.             |
| Photo labelling fails                                    | Classification continues from the text alone.                                  |

**Configuration**

- Environment: `BEDROCK_MODEL_ID` (required, no default), `AWS_REGION`, `UPLOAD_BUCKET_NAME` and the table names above.
- IAM for the worker: `bedrock:InvokeModel`, `rekognition:DetectLabels`, read on S3 `uploads/*`, read and write on the ticket tables.

**Not decided yet**

- Safety keywords are English only. Thai phrases are not detected yet, so a Thai report of fire or gas is triaged by the matrix alone.
- A hazard report the AI could not classify stays `RECEIVED` and is only logged. The 5-minute fallback to the manager's queue as `MEDIUM` (SLA-06) needs the scheduler of SCFRMS-42, and no one is alerted yet.
- The receipt with the emergency numbers 191, 199 and 1669 (SLA-02) is built in the LINE messages of SCFRMS-45 (below); it still needs the real building security phone number.
- Bedrock model ID and region. The worker has not been run against a real model; the impact and urgency wording in the prompt is a first draft to test and tune.
- How a manager finds and re-triages tickets the AI could not classify. For now they are `RECEIVED` tickets in `GET /tickets`; there is no re-run job and no separate queue.
- Per-team SLA hours (the code supports overrides; none are set) and whether reopening a ticket resets its deadline.

## Work order email (SCFRMS-46)

When AI triage assigns a ticket, the assigned team receives a plain-text work order email through Amazon SES.

**Trigger.** The `TRIAGED` event (written in the same transaction as the triage update) starts the notification worker through the `TicketEvents` stream and sends the email. `CREATED` does not send email; it sends the LINE receipt (see LINE messages below).

**No duplicates.** The stream can deliver a record more than once, and the API contract says retries must not send duplicates. For each audit event, channel and recipient the worker checks the `Notifications` table, sends, then writes the record. The email has one recipient, the ticket's team, so its key looks like `tkt_1_triaged#EMAIL_TEAM:PLUMBING`:

| Field             | Value                                  |
| ----------------- | -------------------------------------- |
| `ticketId`        | the ticket (PK)                        |
| `notificationKey` | `<eventId>#<channel>:<recipient>` (SK) |
| Other fields      | `eventId`, `channel`, `sentAt`         |

The record is written with `attribute_not_exists(ticketId)`, so writing it twice is harmless. Delivery is at-least-once: if the worker fails between the send and the write, the email can be sent twice, but it is never lost.

**Recipient.** The `email` field of the team's record in the `Teams` table. While `TEAMS_TABLE_NAME` is not set, or the record has no address, the `TEAM_EMAILS` environment variable is the fallback.

**Email.** Subject: `[<priority>] Work order <ticketId> - <teamId>`. The subject only contains values the system generated, never text written by a resident. The body lists the ticket id, priority, category, location, report time, deadline (shown as Asia/Bangkok time; stored times stay UTC) and description, plus a link when `ADMIN_DASHBOARD_URL` is set. The link format `<ADMIN_DASHBOARD_URL>/tickets/<ticketId>` is an assumption to confirm with the admin dashboard.

**Failures**

| Case                                                        | Result                                                             |
| ----------------------------------------------------------- | ------------------------------------------------------------------ |
| Team has no address in `Teams` or `TEAM_EMAILS`             | Logged as an error, nothing recorded, not retried.                 |
| Ticket no longer exists                                     | Logged, not retried.                                               |
| SES, `Teams` or DynamoDB error, or `SES_SENDER_EMAIL` unset | Reported as a batch item failure; Lambda retries from that record. |

**Configuration**

- Environment: `SES_SENDER_EMAIL`, `TEAMS_TABLE_NAME` (optional until the table exists), `TEAM_EMAILS` (JSON object of team id to address, for example `{"PLUMBING": "plumbing@example.com"}`, the fallback), optional `ADMIN_DASHBOARD_URL`, `AWS_REGION` and the table names above.
- IAM for the worker: `ses:SendEmail`, read on `Tickets`, `TicketPhotos` and `Teams`, and read and write on `Notifications`.
- SES: the sender address or domain must be verified. A new SES account starts in sandbox mode, which only delivers to verified addresses, so request production access before real use.

**Not decided yet**

- The admin dashboard URL and ticket page path.
- Whether a ticket that is re-assigned or reopened should send a new work order; only the first triage sends one today.

## LINE messages (SCFRMS-45)

The reporter gets Flex Messages in LINE, pushed by the same notification worker as the work order email. The message builders are in `backend/src/notifications/line-flex.ts` and the channel in `line-notification.ts`.

**Recipients.** Every reporter of the ticket, read from the `TicketReporters` table, so a ticket merged from several reports reaches everyone. Each reporter is tracked on their own in the notification log, using a key such as `tkt_1_triaged#LINE_REPORTER:<lineUserId>`. A LINE user id is stored in that key but never written to application logs (SR-35): logs only name the channel.

**Messages**

| Audit event kind                           | Message                                                          | State                           |
| ------------------------------------------ | ---------------------------------------------------------------- | ------------------------------- |
| `CREATED`                                  | Receipt with the ticket id, location and time                    | Sent                            |
| `TRIAGED`                                  | Assignment notice naming the team                                | Sent                            |
| `STATUS_CHANGED`, `toStatus` `IN_PROGRESS` | Work started notice                                              | Sent                            |
| `STATUS_CHANGED`, `toStatus` `DONE`        | Completion notice with the proof photo, View details and Re-open | Sent                            |
| `MERGED`                                   | Merge notice                                                     | Not built; belongs to SCFRMS-44 |

**Content rules** (Security, Roles & SLA requirements)

- SLA-02: every receipt says this chat is not an emergency channel and lists the Thai emergency numbers 191 (police), 199 (fire) and 1669 (ambulance), plus building security's number and a call button when `BUILDING_SECURITY_PHONE` is set. A receipt whose description matches a safety hazard keyword also gets a red "possible emergency" banner. The numbers are on every receipt, not only the detected ones, because the keyword scan is English only and a Thai report of a fire would otherwise get no numbers.
- SR-32: resident-written text is cut to a short length and stripped of control characters. The description is never copied into a message; only the location is, shortened.
- RR-04: the reporter sees the team name only, never staff names or internal notes.
- The assignment and later messages carry no priority or deadline.

**Buttons open the LIFF app** (proposal). "View report" and "View details and photo" open `<LIFF_URL>/tickets/<ticketId>`; "Re-open" opens `<LIFF_URL>/tickets/<ticketId>/reopen`. The LIFF app calls the API with the reporter's LINE token, which `POST /tickets/{ticketId}/reopen` needs, and the page can ask `GET /tickets/{ticketId}/photos/{photoId}/access` for a fresh photo link. Because buttons open a page instead of sending a postback to a webhook, there is no LINE webhook and SR-06 (check `X-Line-Signature`) does not apply. Add a webhook only if a postback button is introduced later.

**Proof photo.** The completion notice shows the repair photo, because the Jira task asks for it. LINE only shows an image in a Flex Message when it is an HTTPS JPEG or PNG of at most 1024 by 1024 pixels and about 1 MB, and a phone photo is much bigger. So the backend, not the technician or the reporter, makes a small copy (`backend/src/shared/proof-photo.ts`, image library `sharp`):

1. The technician uploads the original photo; it stays in S3 untouched as the record.
2. When the `STATUS_CHANGED` event for `DONE` arrives, the worker finds the photo named by the event's `proofPhotoId`. If a small copy already exists it is reused, otherwise the worker reads the original (up to 25 MB), turns it upright by its EXIF orientation, fits it inside 1024 by 1024 pixels (never enlarging it, transparency on white) and saves a JPEG under 900 KB (quality 80, then 65, 50 and 35 until it fits) at `thumbnails/REPAIR_PROOF/<ticketId>/<photoId>.jpg`. Re-encoding drops the EXIF data, including any GPS position.
3. The worker signs a short-lived read URL for the small copy (`PROOF_PHOTO_URL_TTL_SECONDS`, default 900, from 60 to 900: SR-23 allows 15 minutes at most) and puts it in the card.
4. If any step fails (a broken or unsupported file, a file over 25 MB, an S3 error, a link LINE would reject), the card is sent without a photo and the buttons still work. The reporter is told either way; the failure is logged.

The signed URL expires after at most 15 minutes, far sooner than the message stays in the chat, so an old card no longer shows the photo; the reporter taps "View details and photo" to see the full photo through the LIFF page. The ticket API still never returns a permanent photo URL or an S3 key.

Not verified on real AWS yet: a URL signed with a Lambda role's temporary credentials carries a long session token, and LINE accepts image URLs of at most 2000 characters. A longer URL is detected and the card goes out without the photo; if that happens in practice, sign with CloudFront signed URLs instead. Such a URL also stops working when the role's credentials expire, even if the lifetime is longer.

**Failures**

| Case                                                         | Result                                                             |
| ------------------------------------------------------------ | ------------------------------------------------------------------ |
| LINE rejects the message for good (for example status 400)   | Logged with the status, nothing recorded, not retried.             |
| Temporary LINE error (401, 403, 429, 5xx) or any other error | Reported as a batch item failure; Lambda retries from that record. |
| One reporter fails after another was messaged                | The first is already recorded and is skipped on the retry.         |
| The proof photo link cannot be made                          | The completion notice is sent without the photo; logged.           |
| LINE already accepted the same retry key (status 409)        | Counted as sent; LINE remembers a retry key for 24 hours.          |

**Configuration**

- Environment: `LINE_CHANNEL_ACCESS_TOKEN`, `BUILDING_SECURITY_PHONE` (optional), `LIFF_URL` (optional; buttons are left out when it is not an https URL), `UPLOAD_BUCKET_NAME` and `PROOF_PHOTO_URL_TTL_SECONDS` (optional) for the proof photo, and the table names above. SR-34 says the channel secret and access token must live in AWS Secrets Manager, not in files or Git, so the infrastructure should fill `LINE_CHANNEL_ACCESS_TOKEN` from there at deploy time.
- IAM for the worker: read on `Tickets`, `TicketPhotos` and `TicketReporters`, and read and write on `Notifications`. For the proof photo: `s3:GetObject` on the originals (`uploads/REPAIR_PROOF/*`), and `s3:PutObject` and `s3:GetObject` on `thumbnails/*` (the signed URL works only if the signing role can read the copy).
- LINE: the LIFF channel and the Messaging API channel must sit under the same LINE provider, and the reporter must have added the Official Account as a friend, or the push fails (SR-05).
